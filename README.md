# ボートレース3連単予測ボット

LINEでレース場とレース番号を送ると、3連単の推奨買い目と根拠を返す個人用ボット。
インフラ・データ・LINE API すべて無料枠で動く。

```
あなた: 大村 1
ボット: 🚤 大村 1R  締切 15:23

       【推奨買い目（期待値1.05超・確率順）】
       1. 1-3-6   2.7% / 40.8倍 / EV 1.10
       2. 1-3-4   2.4% / 44.4倍 / EV 1.09

       【的中率トップ】
       1. 1-3-5  10.0% /  7.3倍 / EV 0.73
       2. 1-3-2   7.3% /  8.9倍 / EV 0.65
       3. 3-1-5   4.1% / 20.8倍 / EV 0.84

       【根拠】
       ・1号艇 菊地敬介(B1・当地勝率5.06・モーター2連率45.5%)が1着本命。1着確率50.4%
       ・最有力の1-3-5は7.3倍で期待値0.73。売れすぎで妙味なし
       ・確率は市場オッズを事前分布としてモデルで補正した値
```

推奨が2点しかないのは正常です。控除率25%の市場では、買う価値のある買い目は
そもそも滅多にありません。1点もなければ「見送り推奨」と返します。

## 現時点の実力（正直な数字）

2023-07〜2026-04 の154,185レースで学習し、**学習に使っていない**
2026-05-01〜2026-07-24 の13,247レースで検証した結果:

| 指標 | 結果 | 比較対象 |
|---|---|---|
| 1着の的中率 | **57.2%** | 1号艇固定 54.7% / 線形 56.6% |
| 3連単NLL（商品指標・対称測定） | **3.853** | 線形 3.858 / 1着のみ学習のGBM 3.871 |
| 3連単 素の確率上位5点の的中率 | **33.6%** | 線形 33.1% |
| 3連単 素の確率上位5点の回収率 | **78.3%** | 無作為 75.0% / 線形 76.9% |
| 最有力に選ばれた組の種類 | 106通り / 120 | 1-2-3固定なら1通り |

モデルは LightGBM の lambdarank（150本×31葉）で、ラベルは 1着=3・2着=2・3着=1。
「1着だけ」をラベルにすると2・3着の並びの情報が捨てられ、**商品指標である
3連単では線形モデルより悪化する**ことが分かったため、3着まで学習させています。

なお温度キャリブレーションを持つモデルと持たないモデルの LogLoss を
そのまま比べると差が水増しされます（実測で「改善0.036のうち0.025が温度の産物」）。
上の表は新旧とも同一手順（温度・段階指数を評価窓で再推定）で測った公平な値です。
週次の自動採用ゲートも同じ対称プロトコルで判定します。

初期のモデルはこれより良い数字（回収率78.4%）を出していましたが、
**学習データに「結果でしか分からない情報」が混入していたため**で、
実運用ではその数字は出ません（詳細はコミット履歴のリーク修正を参照）。
現在の数字はリーク除去後の正直な値です。

**現状、長期的にはまだ負けます。** 舟券の払戻率は75%（控除率25%）なので、
上の回収率は「無作為より約2ポイント良い」だけで、100%には届いていません。
なおこの表は「モデル素の確率で上位5点を買う」場合の数字で、
本番の買い方（市場ブレンド+期待値フィルタ）の回収率は
オッズ履歴が貯まるまで測定できません。

一方で、これは「1-2-3を買い続ける」ようなボットではありません。
最有力として選ばれた組み合わせは120通り中101通りに散らばっており、
レースごとに1号艇の強さ・展示タイム・気象を見て本命が変わります。

### 100%を超えるために足りないもの

1. **オッズの履歴**（最重要）
   公式は過去オッズを公開していないため、「期待値1.05超だけ買う」戦略の
   回収率を検証できていません。`pipeline/snapshot_odds.py` を回して
   今日からオッズを貯めてください。数週間で検証可能になります。
2. **平均ST・F数・進入予想** — 出走表ページにはあるが、過去データの一括
   ダウンロードには含まれないため未使用。
3. ~~LightGBM への差し替え~~ — 済み。3連単NLL（対称測定）で 3.858 → 3.853。

## 仕組み

### 1. 各艇の強さをスコア化

出走表・直前情報から51個の特徴量を作り、LightGBM（lambdarank）で
効用 `v_i` を出します。レース内の6艇を相対比較するランキング損失で学習しており、
バイナリ分類や線形モデルより一貫して良い確率が得られました。
出力スコアは検証期間で推定した温度 t を掛けてキャリブレーションしています。

推論は Cloudflare Workers 上の自前の木トラバーサル（`worker/src/gbm.ts`）で行い、
lightgbm 本体と**誤差ゼロで一致**することを学習時とテストの両方で検証しています。

主要な特徴量:

- 枠番、場×枠の1着率（大村の1コースは約60%、戸田は約50%と場差が大きい）
- 全国勝率・当地勝率・2連対率・級別
- モーター2連対率・ボート2連対率
- 展示タイム（レース内平均との差）
- 風速・波高 × 枠 の交互作用
- **全国勝率 × 枠 の交互作用** ← 「1枠でも弱い選手」を表現する要
- **選手 × 枠 の実績**（過去データからベイズ縮小推定）

### 2. Plackett-Luce モデルで120通りに展開

1着だけでなく着順全体の確率を、スコアから整合的に導きます。

```
P(i→j→k) = s_i/Σs · s_j^α/Σ(残り) · s_k^β/Σ(残り)
```

素の Plackett-Luce は全段階で指数1を仮定しますが、実際のボートレースでは
**1着が決まった後の2・3着争いの方が横並びに近い**ため、学習で
`α = 0.69`、`β = 0.49` を推定して使っています。ここを1のままにすると
穴目の確率が過大評価され、「期待値の高い買い目」が万券ばかりになります。

120通りの確率の合計はちょうど1になります。

### 3. 市場オッズとブレンドする

**モデル単体の確率をそのまま使ってはいけません。**

初回の実運用で「1.0% × 946.5倍 = 期待値9.65」という買い目が推奨されました。
控除率25%の市場で回収率965%はあり得ません。原因はモデルの確率分布が市場より平らで、
穴目を系統的に過大評価していたことです。

オッズは何千人もの予想が集約されたもので、単体の線形モデルよりずっと正確です。
そこで市場を事前分布、モデルを補正項として対数線形プーリングします。

```
p_final ∝ q_market^(1-λ) · p_model^λ      (λ = 0.25)
```

λ を小さくするほど市場寄りになります。裏を返すと、**このボットの edge は
「市場からの小さなズレ」からしか生まれません。** それが控除率25%の市場で戦うということです。

λ = 0.25 は根拠のない暫定値です。`snapshot_odds.py` のオッズが数週間たまったら
実測して決めてください。

### 4. 期待値でフィルタ

`EV = ブレンド後の確率 × オッズ` を計算し、次をすべて満たす買い目だけを推奨します。

| 条件 | 値 | 理由 |
|---|---|---|
| 期待値の下限 | 1.05 | オッズは締切まで動くので余裕を持たせる |
| 期待値の上限 | 2.5 | これを超えるのは妙味ではなくモデルの誤り |
| 確率の下限 | 1% | 当たる見込みが薄すぎるものは実用性がない |
| モデル/市場の確率比 | 4倍まで | 市場から極端に離れた見立ては外挿 |

並び順は期待値順ではなく**確率順**です。期待値順にすると構造上かならず万券が上に来ますが、
実際に的中する見込みは低いためです。

該当がなければ **「見送り推奨」** と返します。これが一番大事な機能です。

## 構成

```
kyoutei-bot/
├── pipeline/              Python: データ収集・学習・検証
│   ├── download.py        番組表(B)/競走成績(K) の LZH をダウンロード
│   ├── parsers.py         固定長テキストのパーサ（バイト位置で切り出す）
│   ├── build_db.py        SQLite へ取り込み
│   ├── features.py        特徴量の定義 ★worker/src/features.ts と対で管理
│   ├── plackett_luce.py   120通りへの展開
│   ├── model_io.py        モデル読込と木の推論 ★worker/src/gbm.ts と対で管理
│   ├── train.py           線形モデル（比較基準として保持）
│   ├── train_gbm.py       本番モデルの学習（LightGBM lambdarank）
│   ├── backtest.py        的中率・回収率の検証
│   ├── snapshot_odds.py   オッズを貯める（将来の期待値検証用）
│   └── export_fixture.py  TS とのパリティテスト用データ生成
│
├── worker/                TypeScript: Cloudflare Workers 上の LINE ボット
│   ├── src/
│   │   ├── index.ts       Webhook・ルーティング
│   │   ├── line.ts        署名検証・Flex Message
│   │   ├── scrape.ts      boatrace.jp から出走表/直前情報/オッズ
│   │   ├── features.ts    特徴量 ★features.py と完全に一致させる
│   │   ├── gbm.ts         LightGBMの木トラバーサル ★model_io.py と完全に一致させる
│   │   ├── plackettLuce.ts 120通りへの展開
│   │   ├── selection.ts   市場ブレンドと買い目の絞り込み
│   │   ├── predict.ts     推論と根拠の生成
│   │   ├── settle.ts      予想の答え合わせ（Cron Triggerから）
│   │   ├── stats.ts       実運用成績の集計
│   │   └── model.json     学習済みの重み（GitHub Actions が更新）
│   └── test/              44本のテスト（実HTMLを使った結合テスト込み）
│
├── .github/workflows/
│   ├── daily-data.yml     毎朝、前日の結果を取り込む
│   ├── weekly-train.yml   毎週、再学習して改善していれば自動デプロイ
│   ├── snapshot-odds.yml  30分おきにオッズを保存
│   ├── canary.yml         毎日、本番が正常か検証してLINEに通知
│   └── keepalive.yml      毎月、スケジュール無効化を防ぐ
│
└── data/                  ダウンロードしたデータ（gitignore対象）
```

### なぜ Python と TypeScript に分かれているのか

Cloudflare Workers は無料枠が広く常時起動でスリープもないので LINE の
Webhook に最適ですが、JavaScript ランタイムなので Python の機械学習
ライブラリが動きません。そこで **学習は GitHub Actions（Python）、
推論は Workers（TypeScript）** に分離しています。

この構成の唯一の弱点は、特徴量の実装が2つに分かれることです。
片方だけ直すと学習した重みが無意味になり、しかも
「なんとなく動いているが予想が微妙」という気づきにくい壊れ方をします。
そのため `npm test` で**両者の数値が完全一致することを検証**しています。

## セットアップ

### 1. データを集めて学習する

```bash
cd pipeline
pip install -r requirements.txt

# 3年分ダウンロード（8並列で30〜50分。中断しても再実行すれば続きから）
python download.py --start 2023-08-01 --end 2026-07-24 --workers 8

# SQLite に取り込む（CPUコア数に応じて並列パース）
python build_db.py --start 2023-08-01 --end 2026-07-24 --jobs 4

# 学習（直近3か月は検証用に残す）
python train_gbm.py --train-end 2026-04-30 --out ../worker/src/model.json

# 検証
python backtest.py --start 2026-05-01

# TypeScript とのパリティテスト用データを生成
python export_fixture.py
```

**どのくらいの期間を集めるべきか**

3年分を推奨します。現行モデルは3年分（約15万レース）で学習しています。

かつてこのREADMEには「6ヶ月で頭打ち」という学習曲線の表がありましたが、
あれは**リーク混入時代のパイプラインで測った値**で、現在のコードでは
再現しません（リークを除いた現行モデルは3年分で学習したものが最良でした）。
古い測定に基づく結論だったため、表ごと撤回します。

3年より前まで遡らないのは、モーター・ボートが毎年入れ替わり、
選手の級別も半年ごとに変わるため、古すぎるデータは現在のレース傾向と
乖離するからです。過去のB/Kファイルは公式にアーカイブされているので、
必要になれば後からいつでも取得できます。

> **急ぐべきなのはオッズの方です。** 公式は過去オッズを公開していないため、
> `snapshot_odds.py` を今日から回さないと「期待値1.05超だけ買う」戦略の
> 回収率は永久に検証できません。

**並列数について**

1リクエストあたりのサーバ応答が5〜10秒かかるため、直列だと極端に遅くなります。
並列化は待ち時間を重ねるだけなので、既定の8並列でも実効レートは毎秒1〜2件程度で、
ブラウザで普通に閲覧するのと大差ありません。上限は32に制限しています。
公営競技の公式サイトなので、必要以上に上げないでください。

> Windows で `data/` がネットワークドライブや同期フォルダ（OneDrive等）の
> 上にあると SQLite が `disk I/O error` を出すことがあります。その場合は
> `--db C:\temp\kyotei.db` のようにローカルパスを指定してください。

### 2. LINE公式アカウントを作る

1. [LINE Developers](https://developers.line.biz/) でプロバイダーとチャネル
   （Messaging API）を作成
2. **チャネルシークレット**と**チャネルアクセストークン（長期）**を控える
3. 「応答メッセージ」をオフ、「Webhook」をオンにする

**応答メッセージ（Reply API）は通数にカウントされません。**
自分が話しかけて返してもらう使い方なら完全無料です。
（無料枠の月200通を消費するのは Push 通知のみ）

### 3. Cloudflare Workers にデプロイ

> `npx wrangler d1 create kyoutei` が出力する `database_id` を
> `wrangler.toml` に貼る手順が途中に挟まります。
> コマンドをまとめて貼り付けると必ずここでズレるので、1つずつ実行してください。

> ⚠️ **wrangler は `.env` を読みません。** ここを間違えると
> トークンが渡らず Webhook が 401 で落ちます。
>
> | 用途 | 置き場所 |
> |---|---|
> | ローカル開発（`wrangler dev`） | `worker/.dev.vars` |
> | デプロイ先 | `npm run secrets`（内部で wrangler secret put を呼ぶ） |
>
> `.dev.vars.example` を用意してあるのでコピーして使ってください。
> `.env` / `.dev.vars` はどちらも `.gitignore` 済みです。

```bash
# 秘密情報の誤コミットを防ぐフックを有効化（クローン後に一度だけ）
git config core.hooksPath .githooks

cd worker
npm install

# ローカル開発用の環境変数
cp .dev.vars.example .dev.vars   # ← コピーした .dev.vars の方に実際の値を書く

# D1（予想の記録用）を作成し、出力された database_id を wrangler.toml に貼る
npx wrangler d1 create kyoutei
npx wrangler d1 execute kyoutei --remote --file=./schema.sql

# デプロイ先の秘密情報を .dev.vars から登録する。
# 手入力はタイプミスに気づけず「デプロイは通るがWebhookが401」になるので使わない。
npm run secrets

npm test      # 44本のテストが通ることを確認
npm run deploy
```

デプロイ後に出る `https://kyoutei-bot.<subdomain>.workers.dev/webhook` を
LINE Developers の Webhook URL に設定します。

### 4. 動作確認

```bash
# ブラウザから直接（LINEを介さずに確認できる）
https://kyoutei-bot.<subdomain>.workers.dev/predict?jcd=24&rno=12
https://kyoutei-bot.<subdomain>.workers.dev/predict?jcd=24&rno=12&format=json
```

LINE で「大村 12」と送って返ってくれば完成です。

## 使い方

| 送る内容 | 動作 |
|---|---|
| `大村 12` | 大村12Rの予想 |
| `おおむら12` | 同上（ひらがな・カタカナ可） |

`.dev.vars` に書いて `npm run secrets` を実行し直してください。

## 運用と改善

**普段やることはありません。** LINEで予想を聞くだけです。

再学習は検証データの指標で自動判定し、改善しているときだけデプロイします。
本番の死活監視も毎日走り、異常があればLINEに通知が飛びます。

初回だけ必要な設定（Cloudflare APIトークン等）と、
唯一自動化できない「スクレイパーの修復」については
[MAINTENANCE.md](MAINTENANCE.md) を参照してください。

予想を出すたびに D1 の `predictions` テーブルへ記録され、
Cron Trigger（JST 23:30 / 翌 5:00）が実際の結果と払戻金を書き戻します。
LINE で「成績」と送ると集計が見られます。

**バックテストの78.4%は過去データ上の数字で、実運用の成績とは別物です。**
市場ブレンドを入れた今の実装の実績はまだゼロなので、
しばらくは「モデルの言うことが当たっているか」を確かめる期間として使ってください。
数百件たまるまでは、出てくる数字はほぼ運です。

答え合わせを手動で走らせたいときは:

```bash
curl -X POST https://kyoutei-bot.<subdomain>.workers.dev/settle
```

週次の再学習は自動でPRが作られます。バックテストの数字を見てから
マージしてください（自動マージはしません）。

### スクレイパーが壊れたら

boatrace.jp のマークアップが変わると `npm test` が落ちます。

```bash
cd worker
node scripts/fetch-fixtures.mjs 22 1 20260720   # 最新HTMLを取り直す
npm test                                        # どこが壊れたか確認
```

`test/scrape.test.mjs` に期待値が書いてあるので、そこを見ながら
`src/scrape.ts` を直します。
