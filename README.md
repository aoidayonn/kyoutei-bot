# ボートレース3連単予測ボット

LINEでレース場とレース番号を送ると、3連単の推奨買い目と根拠を返す個人用ボット。
インフラ・データ・LINE API すべて無料枠で動く。

```
あなた: 大村 12
ボット: 🚤 大村 12R  締切 20:35

       【期待値トップ】
       1-3-4   4.1% / 28.7倍 / EV 1.18
       3-1-2   3.4% / 35.0倍 / EV 1.19

       【的中率トップ】
       1-2-3  11.8% /  7.2倍 / EV 0.85

       【根拠】
       ・1号艇 山田(A1・当地勝率7.21・モーター2連率48%)が1着本命。1着確率58.2%
       ・展示タイム最速は3号艇 6.71秒
       ・晴 / 風3m / 波2cm
       ・最有力の1-2-3は7.2倍で期待値0.85。売れすぎで妙味なし
```

## 現時点の実力（正直な数字）

2025-07-01〜2026-04-30 の45,587レースで学習し、**学習に使っていない**
2026-05-01〜2026-07-24 の13,247レースで検証した結果:

| 指標 | 結果 | 比較対象 |
|---|---|---|
| 1着の的中率 | **56.3%** | 1号艇を買い続けると 54.7% |
| 3連単 上位5点の的中率 | **32.2%** | — |
| 3連単 上位5点の回収率 | **78.4%** | 無作為に買うと 75.0% |
| 最有力に選ばれた組の種類 | 114通り / 120 | 1-2-3固定なら1通り |

**現状、長期的にはまだ負けます。** 舟券の払戻率は75%（控除率25%）なので、
回収率78.4%は「無作為より3.4ポイント良い」だけで、100%には届いていません。

一方で、これは「1-2-3を買い続ける」ようなボットではありません。
最有力として選ばれた組み合わせは120通り中114通りに散らばっており、
レースごとに1号艇の強さ・展示タイム・気象を見て本命が変わります。

### 100%を超えるために足りないもの

1. **オッズの履歴**（最重要）
   公式は過去オッズを公開していないため、「期待値1.05超だけ買う」戦略の
   回収率を検証できていません。`pipeline/snapshot_odds.py` を回して
   今日からオッズを貯めてください。数週間で検証可能になります。
2. **平均ST・F数・進入予想** — 出走表ページにはあるが、過去データの一括
   ダウンロードには含まれないため未使用。
3. **LightGBM への差し替え** — 現在は線形モデル。非線形の相互作用を
   取り込めば精度は上がるはず。

## 仕組み

### 1. 各艇の強さをスコア化

出走表・直前情報から51個の特徴量を作り、線形結合して効用 `v_i` を出します。

主要な特徴量:

- 枠番、場×枠の1着率（大村の1コースは約60%、戸田は約50%と場差が大きい）
- 全国勝率・当地勝率・2連対率・級別
- モーター2連対率・ボート2連対率
- 展示タイム（レース内平均との差）
- 風速・波高 × 枠 の交互作用
- **全国勝率 × 枠 の交互作用** ← 「1枠でも弱い選手」を表現する要
- **選手 × 枠 の実績**（過去データからベイズ縮小推定）

### 2. Plackett-Luce モデルで120通りに展開

1着だけでなく着順全体の確率を、スコアから整合的に導きます。

```
P(i→j→k) = s_i/Σs · s_j^α/Σ(残り) · s_k^β/Σ(残り)
```

素の Plackett-Luce は全段階で指数1を仮定しますが、実際のボートレースでは
**1着が決まった後の2・3着争いの方が横並びに近い**ため、学習で
`α = 0.87`、`β = 0.62` を推定して使っています。ここを1のままにすると
穴目の確率が過大評価され、「期待値の高い買い目」が万券ばかりになります。

120通りの確率の合計はちょうど1になります。

### 3. 期待値でフィルタ

締切前の生オッズを取得して `EV = 確率 × オッズ` を計算し、
`EV ≥ 1.05` かつ `確率 ≥ 0.5%` の買い目だけを推奨します。
該当がなければ **「見送り推奨」** と返します。これが一番大事な機能です。

## 構成

```
kyoutei-bot/
├── pipeline/              Python: データ収集・学習・検証
│   ├── download.py        番組表(B)/競走成績(K) の LZH をダウンロード
│   ├── parsers.py         固定長テキストのパーサ（バイト位置で切り出す）
│   ├── build_db.py        SQLite へ取り込み
│   ├── features.py        特徴量の定義 ★worker/src/features.ts と対で管理
│   ├── plackett_luce.py   120通りへの展開
│   ├── train.py           最尤推定（L-BFGS）+ 段階指数の推定
│   ├── backtest.py        的中率・回収率の検証
│   ├── snapshot_odds.py   オッズを貯める（将来の期待値検証用）
│   └── export_fixture.py  TS とのパリティテスト用データ生成
│
├── worker/                TypeScript: Cloudflare Workers 上の LINE ボット
│   ├── src/
│   │   ├── index.ts       Webhook・ルーティング
│   │   ├── line.ts        署名検証・Flex Message
│   │   ├── scrape.ts      boatrace.jp から出走表/直前情報/オッズ
│   │   ├── features.ts    特徴量 ★features.py と完全に一致させる
│   │   ├── plackettLuce.ts
│   │   ├── predict.ts     推論と根拠の生成
│   │   └── model.json     学習済みの重み（GitHub Actions が更新）
│   └── test/              18本のテスト（実HTMLを使った結合テスト込み）
│
├── .github/workflows/
│   ├── daily-data.yml     毎朝、前日の結果を取り込む
│   ├── weekly-train.yml   毎週、再学習してPRを作る
│   └── snapshot-odds.yml  1日4回、オッズを保存
│
└── data/                  ダウンロードしたデータ（gitignore対象）
```

### なぜ Python と TypeScript に分かれているのか

Cloudflare Workers は無料枠が広く常時起動でスリープもないので LINE の
Webhook に最適ですが、JavaScript ランタイムなので Python の機械学習
ライブラリが動きません。そこで **学習は GitHub Actions（Python）、
推論は Workers（TypeScript）** に分離しています。

この構成の唯一の弱点は、特徴量の実装が2つに分かれることです。
片方だけ直すと学習した重みが無意味になり、しかも
「なんとなく動いているが予想が微妙」という気づきにくい壊れ方をします。
そのため `npm test` で**両者の数値が完全一致することを検証**しています。

## セットアップ

### 1. データを集めて学習する

```bash
cd pipeline
pip install -r requirements.txt

# 3年分ダウンロード（8並列で30〜50分。中断しても再実行すれば続きから）
python download.py --start 2023-08-01 --end 2026-07-24 --workers 8

# SQLite に取り込む（CPUコア数に応じて並列パース）
python build_db.py --start 2023-08-01 --end 2026-07-24 --jobs 4

# 学習（直近3か月は検証用に残す）
python train.py --train-end 2026-04-30 --out ../worker/src/model.json

# 検証
python backtest.py --start 2026-05-01

# TypeScript とのパリティテスト用データを生成
python export_fixture.py
```

**どのくらいの期間を集めるべきか**

検証セットを固定して学習期間だけを変えた結果:

| 学習期間 | レース数 | 1着的中率 | LogLoss |
|---|---|---|---|
| 4ヶ月 | 18,322 | 56.13% | 1.2335 |
| 6ヶ月 | 27,026 | 56.32% | **1.2284** |
| 8ヶ月 | 35,401 | 56.38% | 1.2292 |
| 10ヶ月 | 45,587 | 56.30% | 1.2287 |

**今の線形モデルは6ヶ月・約27,000レースで頭打ちです。** それ以上足しても
数字は動きません。ボトルネックはサンプル数ではなくモデルの表現力です。

それでも3年分を推奨するのは、LightGBM に差し替えたときに効いてくるからです。
決定木のアンサンブルは51パラメータの線形モデルよりずっとデータを食います。
過去のB/Kファイルは公式にアーカイブされているので、後からいつでも取得できます。

> **急ぐべきなのはオッズの方です。** 公式は過去オッズを公開していないため、
> `snapshot_odds.py` を今日から回さないと「期待値1.05超だけ買う」戦略の
> 回収率は永久に検証できません。

**並列数について**

1リクエストあたりのサーバ応答が5〜10秒かかるため、直列だと極端に遅くなります。
並列化は待ち時間を重ねるだけなので、既定の8並列でも実効レートは毎秒1〜2件程度で、
ブラウザで普通に閲覧するのと大差ありません。上限は32に制限しています。
公営競技の公式サイトなので、必要以上に上げないでください。

> Windows で `data/` がネットワークドライブや同期フォルダ（OneDrive等）の
> 上にあると SQLite が `disk I/O error` を出すことがあります。その場合は
> `--db C:\temp\kyotei.db` のようにローカルパスを指定してください。

### 2. LINE公式アカウントを作る

1. [LINE Developers](https://developers.line.biz/) でプロバイダーとチャネル
   （Messaging API）を作成
2. **チャネルシークレット**と**チャネルアクセストークン（長期）**を控える
3. 「応答メッセージ」をオフ、「Webhook」をオンにする

**応答メッセージ（Reply API）は通数にカウントされません。**
自分が話しかけて返してもらう使い方なら完全無料です。
（無料枠の月200通を消費するのは Push 通知のみ）

### 3. Cloudflare Workers にデプロイ

> ⚠️ **wrangler は `.env` を読みません。** ここを間違えると
> トークンが渡らず Webhook が 401 で落ちます。
>
> | 用途 | 置き場所 |
> |---|---|
> | ローカル開発（`wrangler dev`） | `worker/.dev.vars` |
> | デプロイ先 | `npx wrangler secret put ...` |
>
> `.dev.vars.example` を用意してあるのでコピーして使ってください。
> `.env` / `.dev.vars` はどちらも `.gitignore` 済みです。

```bash
# 秘密情報の誤コミットを防ぐフックを有効化（クローン後に一度だけ）
git config core.hooksPath .githooks

cd worker
npm install

# ローカル開発用の環境変数
cp .dev.vars.example .dev.vars   # ← コピーした .dev.vars の方に実際の値を書く

# D1（予想の記録用）を作成し、出力された database_id を wrangler.toml に貼る
npx wrangler d1 create kyoutei
npx wrangler d1 execute kyoutei --remote --file=./schema.sql

# デプロイ先の秘密情報を登録（.dev.vars とは別に必要）
npx wrangler secret put LINE_CHANNEL_SECRET
npx wrangler secret put LINE_CHANNEL_ACCESS_TOKEN
npx wrangler secret put ALLOWED_USER_ID   # 自分のuserIdだけ許可（任意）

npm test      # 18本のテストが通ることを確認
npm run deploy
```

デプロイ後に出る `https://kyoutei-bot.<subdomain>.workers.dev/webhook` を
LINE Developers の Webhook URL に設定します。

### 4. 動作確認

```bash
# ブラウザから直接（LINEを介さずに確認できる）
https://kyoutei-bot.<subdomain>.workers.dev/predict?jcd=24&rno=12
https://kyoutei-bot.<subdomain>.workers.dev/predict?jcd=24&rno=12&format=json
```

LINE で「大村 12」と送って返ってくれば完成です。

## 運用と改善

`predictions` テーブルに毎回の予想が保存されます。
これがないと「実際どうだったか」を後から検証できないので、
必ず残したまま運用してください。

週次の再学習は自動でPRが作られます。バックテストの数字を見てから
マージしてください（自動マージはしません）。

### スクレイパーが壊れたら

boatrace.jp のマークアップが変わると `npm test` が落ちます。

```bash
cd worker
node scripts/fetch-fixtures.mjs 22 1 20260720   # 最新HTMLを取り直す
npm test                                        # どこが壊れたか確認
```

`test/scrape.test.mjs` に期待値が書いてあるので、そこを見ながら
`src/scrape.ts` を直します。
