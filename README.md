# ボートレース3連単予測ボット

LINEでレース場とレース番号を送ると、3連単の推奨買い目と根拠を返す個人用ボット。
インフラ・データ・LINE API すべて無料枠で動く。

```
あなた: 大村 1
ボット: 🚤 大村 1R  締切 15:23

       【推奨買い目（期待値1.05超・確率順）】
       1. 1-3-6   2.7% / 40.8倍 / EV 1.10
       2. 1-3-4   2.4% / 44.4倍 / EV 1.09

       【的中率トップ】
       1. 1-3-5  10.0% /  7.3倍 / EV 0.73
       2. 1-3-2   7.3% /  8.9倍 / EV 0.65
       3. 3-1-5   4.1% / 20.8倍 / EV 0.84

       【根拠】
       ・1号艇 菊地敬介(B1・当地勝率5.06・モーター2連率45.5%)が1着本命。1着確率50.4%
       ・最有力の1-3-5は7.3倍で期待値0.73。売れすぎで妙味なし
       ・確率は市場オッズを事前分布としてモデルで補正した値
```

推奨が2点しかないのは正常です。控除率25%の市場では、買う価値のある買い目は
そもそも滅多にありません。1点もなければ「見送り推奨」と返します。

---

## このプロジェクトのゴール

舟券の**控除率は約25%**（払戻率75%）。何もしなければ長期回収率は75%に収束します。
したがってゴールは「必ず勝つ」ではなく、**オッズ（＝市場の予想）より正確な確率を出し、
市場が過小評価している買い目だけを抽出する**ことです。

成功基準は**回収率100%超**であり、的中率ではありません。

### やること / やらないこと

| やること | やらないこと |
|---|---|
| 3連単の推奨買い目と根拠を返す | 自動投票（購入判断は必ず人間） |
| 確率・オッズ・期待値を併記する | 資金管理の自動化（ケリー基準等） |
| 買う価値がなければ見送りを勧める | 複数ユーザー対応・課金 |
| 実績を記録して後から検証する | 3連単以外の券種 |

### 唯一の本当のベンチマークは「市場」

上の比較相手（1号艇固定・線形モデル）はどれも**弱すぎます**。
控除率25%の市場で勝つには、市場そのものより正確でなければ意味がありません。

公式は過去オッズを公開していませんが、**払戻金から市場の確率を逆算できます**。
パリミュチュエルでは `払戻金/100 = 0.75 / q_market` なので `q = 0.75 ÷ オッズ`。
的中組についてしか分かりませんが、NLLに必要なのはまさにそれです
（`pipeline/market_edge.py`）。

| 2026-05-01〜07-24, 13,247レース | 3連単NLL |
|---|---|
| **市場（オッズ）** | **3.666** |
| 現行（36ヶ月+全較正） | 3.766 |
| 当節成績+枠ペア較正 | 3.777 |
| 枠ペア較正のみ | 3.791 |
| 初期実装 | 3.853 |

**市場のほうがまだ 0.096 nat 正確です。** 当初の差 0.187 から **ほぼ半分を埋めました**。
的中組に市場より高い確率を置けたレースは 37.5% → 42%超 に増えています。

**つまり現状、このモデルには市場に対するエッジがありません。**
期待値1.05超という判定が出ても、それは市場の歪みではなく**モデルの誤差**です。
（だから λ=0.25 と期待値上限2.5 が必要になっている、とも言えます）

較正前の時点で、選べる区分（レース場・風速・モデルの確信度）を総当たりしても
**delta がプラスになる区分は一つもありませんでした**。24場すべてマイナスです。
`python market_edge.py --start 2026-05-01` で再現できます。

### 市場側に歪みはあるか（53,694レース）

あります。ただし小さいです。

| n番人気を毎回買う | 的中率 | 回収率 |
|---|---|---|
| 1番人気 | 10.81% | 77.2% |
| 2番人気 | 8.71% | **78.9%** |
| 6-10番人気 | 3.49% | 76.8% |
| 21-50番人気 | 0.64% | 68.5% |
| 51番人気以下 | 0.12% | 51.1% |

典型的な **favorite-longshot bias**（人気薄が買われすぎ）が出ています。
市場は完全に効率的ではありません。しかし一番おいしい2番人気でも78.9%で、
**100%までまだ21ポイント**あります。市場の歪みに乗るだけでは到底届きません。

一方で、これは「1-2-3を買い続ける」ボットではありません。最有力に選ばれた
組み合わせは120通り中99通りに散らばっており、レースごとに1号艇の強さ・
展示タイム・気象を見て本命が変わります。

> 上の回収率は「モデル素の確率で上位5点を買う」場合の数字です。
> 本番の買い方（市場ブレンド+期待値フィルタ）の回収率は、
> オッズ履歴が貯まるまで測定できません（§ 100%を超えるために足りないもの）。

### 数字の測り方について

温度キャリブレーションを持つモデルと持たないモデルの LogLoss をそのまま
比べると差が水増しされます（実測で「改善0.036のうち0.025が温度の産物」でした）。
上の表は新旧とも同一手順（温度・段階指数を評価窓で再推定）で測った公平な値です。
週次の自動採用ゲートも同じ対称プロトコルで判定します。

また初期のモデルは回収率78.4%というより良い数字を出していましたが、
**学習データに「結果でしか分からない情報」が混入していたため**でした
（詳細はコミット履歴のリーク修正を参照）。現在の数字は除去後の正直な値です。

### 100%を超えるために足りないもの

必要な差は「無作為（75%）との差」ではなく「市場との差」です。
ある買い目が+EVであるためには `p_true × オッズ > 1`、すなわち
`p_true / q_market > 1.333`。**市場より0.288 nat 正確な組を見つける**必要があります。
現在は平均 −0.096 nat なので、**合計およそ 0.38 nat 分**足りません。

1. ~~**2・3着の条件付き分布を鋭くする**~~ — 済み（枠ペア較正）。
   ~~**当節成績を入れる**~~ — 済み。合わせて市場との差 0.187 → 0.112。
2. **市場が見ていない情報を入れる** — ここが本丸ですが、有望株は
   ほぼ潰れました（下の「試して駄目だったこと」を参照）。
   進入は神の目でも0.009しか改善せず、公開情報の範囲では打ち止めです。
   残る未検証は、締切直前のオッズ変動（賢い金の追跡）、部品交換、選手コメント。
   いずれも「市場が見ているものを後追いする」性質なので、期待は薄いです。
3. **オッズの履歴**（実質これが唯一の残り札）
   `snapshot_odds.py` が30分おきに貯めています。`fit_lambda.py` で
   λ の実測と本番戦略の回収率検証ができます（2026年8月中旬）。

ような「見落としていた情報源」が残っていれば別ですが、主要な候補は潰しました）。

### それでも勝てる可能性が残っている理由

モデル単体が市場に負けていることと、儲からないことは**同じではありません**。
予測の結合では、片方が単体で劣っていても独立な情報を持っていれば
合成が両方に勝ちます。

```
p_final ∝ q_market^(1-λ) · p_model^λ
```

- λ\* が 0 に張り付く → モデルは市場に何も足せていない。この設計では勝てない
- λ\* > 0 で有意 → 市場が見落としている情報がある

**これがまだ一度も測れていません。** 現在の λ=0.25 は根拠のない暫定値です。
過去オッズは公式が公開しておらず、`snapshot_odds.py` で自分で貯めるしかないためです。

貯まったら `pipeline/fit_lambda.py` を回せば、λ の実測と
**本番の買い方の回収率（ブートストラップ信頼区間つき）** が一度に出ます。
これがこのプロジェクトに残された最後の未検証項目です。

### 検証にどれだけの試行が要るか

3連単は分散が非常に大きく、**エッジがあっても確認が困難**です。
的中率10%・平均10倍の買い目で回収率105%を仮定すると、1回あたりの
標準偏差は約3.1。回収率を±1ポイントの精度で測るには
**約10万ベット**、±3ポイントでも**約1万ベット**必要です。

1日5点×十数レースでも数年かかります。
**「数百ベットで回収率120%だった」は、ほぼ確実にただの運です。**

## 仕組み

### 1. 各艇の強さをスコア化

出走表・直前情報から55個の特徴量を作り、LightGBM（lambdarank、150本×31葉）で
効用 `v_i` を出します。ラベルは **1着=3・2着=2・3着=1**。
「1着だけ」をラベルにすると2・3着の並びの情報が捨てられ、商品指標である
3連単では線形モデルより悪化することが分かったため、3着まで学習させています。

出力スコアは検証期間で推定した温度 `t` を掛けてキャリブレーションします。

推論は Cloudflare Workers 上の自前の木トラバーサル（`worker/src/gbm.ts`）で行い、
lightgbm 本体と**誤差ゼロで一致**することを学習時とテストの両方で検証しています。

主要な特徴量（55個）:

- 枠番、場×枠の1着率（大村の1コースは約60%、戸田は約50%と場差が大きい）
- 全国勝率・当地勝率・2連対率・級別
- モーター2連対率・ボート2連対率
- 展示タイム（レース内平均との差）
- 風速・波高 × 枠 の交互作用
- **全国勝率 × 枠 の交互作用** ← 「1枠でも弱い選手」を表現する要
- **選手 × 枠 の実績**（過去データからベイズ縮小推定）
- **当節成績**（同じ節のここまでの走り。出走表の「今節成績」グリッドから取得。
  学習時は自レースより前の結果だけを使いリークを防ぐ）
- レース番号（12R=優勝戦などの番組情報）

### 2. Plackett-Luce モデルで120通りに展開

1着だけでなく着順全体の確率を、スコアから整合的に導きます。

```
P(i→j→k) = P(1着=i) · P(2着=j | 1着=i) · P(3着=k | 1着=i, 2着=j)
```

素の Plackett-Luce は各段階を `exp(v_j)` に比例させますが、これは
**1着が誰であっても2着の相対順位は同じ**という誤った仮定になります。
実データはそうなっていません。

| 2着になる確率 | 1着が1枠のとき | 1着が4枠のとき |
|---|---|---|
| 5枠 | 12.1% | **20.0%** |
| 6枠 | 7.3% | **13.1%** |

外枠がまくると内枠が押し出され、他の外枠が繰り上がります。
段階指数（スカラー）をどう調整してもこの構造は表現できません。
そこで条件付きスコアに枠ペアの項と、2・3着専用の特徴量補正を足します。

```
1着:      v_i + b[i]                           + w1 · x_i
2着: a2 · v_j + A[1着の枠][j]                  + w2 · x_j
3着: a3 · v_k + B[1着の枠][k] + C[2着の枠][k]   + w3 · x_k
```

1着の `b[i] + w1·x_i` は較正窓で推定する残差補正で、
学習後3ヶ月のドリフト（枠の強さの季節変動など）を拾います
（1着LL −0.005、2窓+本番モデルの後半採点で三重に再現）。

A/B/C は 6×6 の行列、w2/w3 は特徴量と同次元。いずれも条件付きロジットなので凸で、
学習期間内の検証区間だけで推定します（`pipeline/stage_calib.py`）。

これで3連単NLLが **3.853 → 3.790**、さらに当節成績の特徴量で **3.776** まで縮みました。
120通りの確率の合計はちょうど1になります。

### 3. 市場オッズとブレンドする

**モデル単体の確率をそのまま使ってはいけません。**

初回の実運用で「1.0% × 946.5倍 = 期待値9.65」という買い目が推奨されました。
控除率25%の市場で回収率965%はあり得ません。原因はモデルの確率分布が市場より平らで、
穴目を系統的に過大評価していたことです。

オッズは何千人もの予想が集約されたもので、単体のモデルよりずっと正確です。
そこで市場を事前分布、モデルを補正項として対数線形プーリングします。

```
p_final ∝ q_market^(1-λ) · p_model^λ      (λ = 0.25)
```

λ を小さくするほど市場寄りになります。裏を返すと、**このボットの edge は
「市場からの小さなズレ」からしか生まれません。** それが控除率25%の市場で戦うということです。

### 4. 期待値でフィルタ

`EV = ブレンド後の確率 × オッズ` を計算し、次をすべて満たす買い目だけを推奨します。

| 条件 | 値 | 理由 |
|---|---|---|
| 期待値の下限 | 1.05 | オッズは締切まで動くので余裕を持たせる |
| 期待値の上限 | 2.5 | これを超えるのは妙味ではなくモデルの誤り |
| 確率の下限 | 1% | 当たる見込みが薄すぎるものは実用性がない |
| モデル/市場の確率比 | 4倍まで | 市場から極端に離れた見立ては外挿 |

並び順は期待値順ではなく**確率順**です。期待値順にすると構造上かならず万券が上に来ますが、
実際に的中する見込みは低いためです。

該当がなければ **「見送り推奨」** と返します。これが一番大事な機能です。

### なぜ Python と TypeScript に分かれているのか

Cloudflare Workers は無料枠が広く常時起動でスリープもないので LINE の
Webhook に最適ですが、JavaScript ランタイムなので Python の機械学習
ライブラリが動きません。そこで **学習は GitHub Actions（Python）、
推論は Workers（TypeScript）** に分離しています。

この構成の弱点は、特徴量と木の推論の実装が2つに分かれることです。
片方だけ直すとモデルが無意味になり、しかも
「なんとなく動いているが予想が微妙」という気づきにくい壊れ方をします。
そのため `npm test` で**両者の数値が完全一致することを検証**しています。

## セットアップ

### 1. データを集めて学習する

```bash
cd pipeline
pip install -r requirements.txt

# 3年分ダウンロード（8並列で30〜50分。中断しても再実行すれば続きから）
python download.py --start 2023-08-01 --end 2026-07-24 --workers 8

# SQLite に取り込む（CPUコア数に応じて並列パース）
python build_db.py --start 2023-08-01 --end 2026-07-24 --jobs 4

# 学習（直近3か月は検証用に残す）
python train_gbm.py --train-end 2026-04-30 --out ../worker/src/model.json

# 検証
python backtest.py --start 2026-05-01

# TypeScript とのパリティテスト用データを生成（再学習したら必ず実行）
python export_fixture.py
```

**どのくらいの期間を集めるべきか**

3年分で十分です。現行モデルで測った学習曲線（3連単NLL・検証窓固定）:

| 学習期間 | 窓1(2026-05〜07) | 窓2(2026-02〜04) |
|---|---|---|
| 6ヶ月 | 3.8725 | — |
| 1年 | 3.8548 | 3.8626 |
| 2年 | 3.8512 | 3.8620 |
| 3年 | 3.8531 | 3.8617 |

**2年以降は平坦です**（2年と3年の優劣は窓によって入れ替わる ±0.002 のノイズ）。
それより古いデータを足しても効かないか、モーター入替・選手の変化による
分布の乖離でわずかに害になります。週次学習は直近36ヶ月のローリング窓に
限定しており、これ以上過去のデータを取得する必要はありません。

> **急ぐべきなのはオッズの方です。** 公式は過去オッズを公開していないため、
> `snapshot_odds.py` を今日から回さないと「期待値1.05超だけ買う」戦略の
> 回収率は永久に検証できません。

**並列数について**

1リクエストあたりのサーバ応答が5〜10秒かかるため、直列だと極端に遅くなります。
並列化は待ち時間を重ねるだけなので、既定の8並列でも実効レートは毎秒1〜2件程度で、
ブラウザで普通に閲覧するのと大差ありません。上限は32に制限しています。
公営競技の公式サイトなので、必要以上に上げないでください。

> Windows で `data/` がネットワークドライブや同期フォルダ（OneDrive等）の
> 上にあると SQLite が `disk I/O error` を出すことがあります。その場合は
> `--db C:\temp\kyotei.db` のようにローカルパスを指定してください。

### 2. LINE公式アカウントを作る

1. [LINE Developers](https://developers.line.biz/) でプロバイダーとチャネル
   （Messaging API）を作成
2. **チャネルシークレット**と**チャネルアクセストークン（長期）**を控える
3. 「応答メッセージ」をオフ、「Webhook」をオンにする

**応答メッセージ（Reply API）は通数にカウントされません。**
自分が話しかけて返してもらう使い方なら完全無料です。
（無料枠の月200通を消費するのは Push 通知のみ）

### 3. Cloudflare Workers にデプロイ

> `npx wrangler d1 create kyoutei` が出力する `database_id` を
> `wrangler.toml` に貼る手順が途中に挟まります。
> コマンドをまとめて貼り付けると必ずここでズレるので、1つずつ実行してください。

> ⚠️ **wrangler は `.env` を読みません。** ここを間違えると
> トークンが渡らず Webhook が 401 で落ちます。
>
> | 用途 | 置き場所 |
> |---|---|
> | ローカル開発（`wrangler dev`） | `worker/.dev.vars` |
> | デプロイ先 | `npm run secrets`（内部で wrangler secret put を呼ぶ） |
>
> `.dev.vars.example` を用意してあるのでコピーして使ってください。
> `.env` / `.dev.vars` はどちらも `.gitignore` 済みです。

```bash
# 秘密情報の誤コミットを防ぐフックを有効化（クローン後に一度だけ）
git config core.hooksPath .githooks

cd worker
npm install

# ローカル開発用の環境変数
cp .dev.vars.example .dev.vars   # ← コピーした .dev.vars の方に実際の値を書く

# D1（予想の記録用）を作成し、出力された database_id を wrangler.toml に貼る
npx wrangler d1 create kyoutei
npx wrangler d1 execute kyoutei --remote --file=./schema.sql

# デプロイ先の秘密情報を .dev.vars から登録する。
# 手入力はタイプミスに気づけず「デプロイは通るがWebhookが401」になるので使わない。
npm run secrets

npm test      # 44本のテストが通ることを確認
npm run deploy
```

デプロイ後に出る `https://kyoutei-bot.<subdomain>.workers.dev/webhook` を
LINE Developers の Webhook URL に設定します。

### 4. 動作確認

```bash
# ブラウザから直接（LINEを介さずに確認できる）
https://kyoutei-bot.<subdomain>.workers.dev/predict?jcd=24&rno=12
https://kyoutei-bot.<subdomain>.workers.dev/predict?jcd=24&rno=12&format=json
```

LINE で「大村 12」と送って返ってくれば完成です。

## 使い方

| 送る内容 | 動作 |
|---|---|
| `大村 12` | 大村12Rの予想 |
| `おおむら12` | 同上（ひらがな・カタカナ・全角数字可） |
| `24 12` | 同上（場コード可） |
| `今日` | 本日の開催場一覧 |
| `成績` | これまでの予想の的中率・回収率 |
| `whoami` | 自分のLINE userId（`ALLOWED_USER_ID` に設定する値） |
| `ヘルプ` | 使い方 |

`ALLOWED_USER_ID` を設定すると、自分以外からのメッセージを無視します。
この値はメッセージを受け取って初めて分かるので、デプロイ後に `whoami` で確認し、
`.dev.vars` に書いて `npm run secrets` を実行し直してください。

## 運用

**普段やることはありません。** LINEで予想を聞くだけです。

毎週月曜に再学習が走り、検証データの指標で**自動判定して改善しているときだけ
デプロイ**します（PRは作りません。人間の承認も不要です）。判定を満たさなければ
何もせず現行モデルのまま動き続けます。どちらの場合もLINEに結果が届きます。

本番の死活監視も毎日走り、異常があればLINEに通知が飛びます。

予想を出すたびに D1 の `predictions` テーブルへ記録され、
Cron Trigger（JST 23:30 / 翌 5:00）が実際の結果と払戻金を書き戻します。
LINE で「成績」と送ると集計が見られます。

> **バックテストの数字は過去データ上のもので、実運用の成績とは別物です。**
> 市場ブレンドを入れた今の実装の実績はまだ蓄積中なので、
> しばらくは「モデルの言うことが当たっているか」を確かめる期間として使ってください。
> 数百件たまるまでは、出てくる数字はほぼ運です。

初回だけ必要な設定（Cloudflare APIトークン等）、障害時の対処、
唯一自動化できない「スクレイパーの修復」は
**[MAINTENANCE.md](MAINTENANCE.md)** にまとめてあります。

## データソースと無料枠

すべて無料で入手できるものだけを使っています。

| 用途 | 取得元 | 形式 |
|---|---|---|
| 過去の出走表（番組表） | [番組表ダウンロード](https://www1.mbrace.or.jp/od2/B/dindex.html) | LZH → 固定長テキスト（日次） |
| 過去のレース結果 | [競走成績ダウンロード](https://www1.mbrace.or.jp/od2/K/dindex.html) | LZH → 固定長テキスト（日次） |
| 当日の出走表 | `boatrace.jp/owpc/pc/race/racelist` | HTMLスクレイピング |
| 直前情報（展示タイム・気象） | `.../race/beforeinfo` | HTMLスクレイピング（発走約40分前） |
| 3連単オッズ | `.../race/odds3t` | HTMLスクレイピング |
| レース結果 | `.../race/raceresult` | HTMLスクレイピング |

公式の「番組表閲覧」「オッズ情報・結果」「競走成績閲覧」サービスは
**2025年3月5日で終了**しています。上記2つのダウンロードサイトは継続中です。

`jcd` はレース場コード（01桐生 … 24大村）。

### 使っている無料枠

| サービス | 無料枠 | 実際の使用量 |
|---|---|---|
| Cloudflare Workers | 100,000 req/日 | 1日数十 req |
| Cloudflare D1 | 5GB | 数MB（予想の記録のみ） |
| Cloudflare Cron Triggers | 無料 | 1日2回 |
| GitHub Actions | publicリポジトリは無制限 | 1日約40分 |
| LINE Messaging API | 応答メッセージは通数無制限 | Reply中心。Pushは通知のみ |

**LINEはPush（自動通知）だけが無料枠 月200通 を消費します。** こちらから
話しかけて返してもらう形（Reply）は完全無料です。通知が飛ぶのは異常検知と
週次の学習結果だけなので、まず超えません。
